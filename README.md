To create the branches, I first had to create an HTML document, add, and commit it to establish a main branch. Once the main branch was established, to create branches off of the main, I made sure I was in the main branch and created the new branches from the main using “git switch -c (branch name)”. Creating each branch from main ensured that every branch started from the same commit, which gave me a clean starting point for comparing changes later. To manage the branches, I simply used “git switch (branch name)” to switch between the different branches and I used “git status” to manage what files were added to the staging area and what new changes need to be committed. To create a conflict I had to make sure that I added code to the same line on different branches. As I merged the first side branch with the main branch, no conflict arose, but as I merged the second side branch with the main branch, a merge conflict arose due to the fact that both branches included a piece of code on the same line. VS Code marked the conflicting lines after which I was left with three options of which I picked to "accept the incoming changes" which kept the version from the branch that I merged in (feature/header branch in this case) as opposed to the main branch. From there I committed the new changes to my git repo and pushed them to my GitHub repo. This assignment showed me that a merge conflict is not an error, but Git asking me to decide which version to keep. It also taught me why checking “git status” often and committing in small steps makes branches much easier to manage.
